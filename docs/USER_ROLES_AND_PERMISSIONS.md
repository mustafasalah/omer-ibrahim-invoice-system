# أدوار المستخدمين والصلاحيات

## 1. النموذج المعتمد

الإصدار الأول يستخدم دورين ثابتين:

- **ADMIN — مدير**
- **EMPLOYEE — موظف**

تُطبّق الصلاحيات في الخادم. إخفاء الزر في الواجهة ليس بديلًا عن التحقق.

## 3. قواعد حساب المستخدم

- اسم المستخدم فريد بعد التطبيع وغير حساس لحالة الأحرف اللاتينية.
- الاسم الظاهر إلزامي.
- كلمة المرور لا تخزن بصورتها الأصلية.
- المستخدم المعطل لا يبدأ جلسة جديدة.
- تعطيل مستخدم ينهي جلساته النشطة.
- لا يمكن تعطيل آخر مدير نشط.
- لا يمكن للمستخدم خفض دوره إذا كان آخر مدير.
- لا يسمح بحذف المستخدم؛ يعطل للحفاظ على الروابط التاريخية.
- الفواتير والحركات تبقى منسوبة للمستخدم المعطل.

## 4. سياسة كلمة المرور

- 10 أحرف على الأقل.
- قبول عبارة مرور طويلة دون اشتراط تعقيد مصطنع.
- رفض كلمات المرور الشائعة جدًا واسم المستخدم.
- السماح حتى 128 حرفًا.
- عدم قص المسافات بصمت داخل كلمة المرور.
- المدير يعين كلمة مؤقتة، ويُطلب تغييرها عند أول دخول.
- بعد إعادة التعيين تُلغى كل الجلسات القديمة.
- لا تعرض كلمة المرور المؤقتة مرة ثانية بعد إنشاء المستخدم.

## 5. الجلسات

- Cookie من نوع HttpOnly وSameSite=Strict.
- الجلسة مرتبطة بمعرف عشوائي مخزن مجزأ.
- انتهاء خمول افتراضي 30 دقيقة.
- عمر أقصى افتراضي 12 ساعة.
- «تذكرني» خارج MVP.
- تغيير كلمة المرور أو التعطيل يلغي الجلسات.
- تسجيل الخروج يلغي جلسة الجهاز الحالي.

## 6. ملكية السجلات

لا يقتصر الموظف على فواتيره؛ يستطيع عرض فواتير المحل كلها لتسهيل العمل. مع ذلك:

- تعرض الواجهة «أنشأها» و«آخر تعديل».
- لا يستطيع الموظف تعديل فاتورة صادرة حتى لو أنشأها.
- يستطيع أي موظف تسجيل دفعة على فاتورة صادرة غير مؤرشفة.
- يسجل النظام منفذ كل عملية، فلا توجد عمليات باسم «النظام» إلا الاشتقاقات الآلية.

## 7. العمليات الحساسة

تتطلب تأكيدًا إضافيًا وسببًا:

- تعديل فاتورة صادرة.
- إلغاء فاتورة.
- تسجيل استرداد.
- إبطال حركة مالية.
- تغيير تنسيق الترقيم بعد وجود فواتير.
- استعادة نسخة احتياطية.
- تعطيل مدير.

تتطلب إعادة إدخال كلمة مرور المدير عند:

- استعادة نسخة احتياطية.
- تجاوز إلغاء فاتورة ذات صافي محصل.
- إعادة تعيين كلمة مرور مدير آخر.

## 8. صلاحيات مقترحة مستقبلًا

تصمم طبقة التفويض باستخدام قدرات داخلية بدل فحص الدور مباشرة، مثل:

```text
invoice.read
invoice.create
invoice.issue
invoice.edit_issued
invoice.cancel
payment.create
refund.create
settings.manage
backup.restore
audit.read
```

في MVP يُترجم الدور الثابت إلى مجموعة قدرات. يتيح ذلك إضافة دور «محاسب» أو صلاحيات مخصصة لاحقًا دون إعادة كتابة كل المسارات.

## 9. الاستجابات عند المنع

- `401 Unauthorized`: لا توجد جلسة صالحة.
- `403 Forbidden`: توجد جلسة لكن القدرة غير متاحة.
- لا يكشف الرد وجود بيانات حساسة لا يملك المستخدم الوصول إليها.
- تعرض الواجهة سببًا مفهومًا: «هذه العملية متاحة للمدير فقط».
- يسجل تكرار محاولات العمليات الحساسة المرفوضة في السجل التقني، لا سجل العمليات التجاري، ما لم تكن ذات دلالة أمنية.

## 10. اختبارات أساسية للصلاحيات

1. لا يستطيع موظف استدعاء API الاسترداد يدويًا.
2. لا يستطيع موظف تعديل فاتورة صادرة بتجاوز الواجهة.
3. تعطيل المستخدم يلغي جلسته فورًا أو خلال مهلة تحقق قصيرة.
4. لا يمكن تعطيل آخر مدير.
5. الاستعادة تتطلب جلسة مدير حديثة وإعادة تحقق.
6. الفاتورة القديمة تعرض اسم مستخدم معطل دون خطأ.
